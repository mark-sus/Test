# Telegram-бот заявок (адмін + виконавці)

Бот з вебінтерфейсом (Telegram Mini App): адміністратор створює заявку у формі,
вона автоматично надсилається обраному виконавцю. Виконавець бачить заявку у
списку, відкриває деталі, копіює ID, тисне «Відкрити на мапі» / «Зателефонувати»,
підтверджує виконання (заявка йде адміну на перевірку) або переносить на інший день.

## Що є в проєкті

```
tg-service-bot/
├─ server.js       # express-сервер: API + роздача вебдодатку
├─ bot.js          # логіка Telegram-бота (Telegraf): /start, сповіщення
├─ db.js           # просте сховище даних у файлі data.json (lowdb)
├─ public/
│  ├─ admin.html      # форма створення заявки (для адміністратора)
│  ├─ requests.html   # список заявок (для виконавця й адміністратора)
│  ├─ request.html    # картка заявки: копіювання, мапа, дзвінок, дії
│  └─ style.css
├─ package.json
└─ .env.example
```

## Як це працює

1. **Адміністратор** пише `/start` боту → отримує кнопку меню «🆕 Нова заявка»,
   яка відкриває `admin.html` прямо в Telegram.
2. Заповнює форму (ID завдання, час, ID наряду, технологія, телефон, локація,
   ID клієнта) і обирає виконавця зі списку — список підтягується автоматично
   з тих, хто хоч раз писав боту `/start`.
3. Після натискання «Створити заявку» бот одразу надсилає обраному
   **виконавцю** повідомлення з кнопкою «Відкрити заявку».
4. **Виконавець** відкриває картку заявки (`request.html`): бачить ID завдання
   і час, ID наряду, технологію, адресу (з посиланням «Відкрити на мапі») і
   телефон (з посиланням «Зателефонувати»). Кнопками з копіюванням можна
   скопіювати ID завдання й ID наряду.
5. Виконавець або **підтверджує** виконання (заявка переходить у статус
   «На перевірці» і бот сповіщає адміністратора), або **переносить** заявку на
   іншу дату (вказує нову дату й коментар — адміністратора також сповіщає бот).
6. **Адміністратор** отримує список заявок, що очікують перевірки, відкриває
   картку і або приймає виконання, або повертає заявку виконавцю на
   доопрацювання — бот повідомляє виконавця про рішення.

## Встановлення

Знадобиться Node.js 18+.

```bash
npm install
cp .env.example .env
```

Заповніть `.env`:

| Змінна | Опис |
|---|---|
| `BOT_TOKEN` | токен від [@BotFather](https://t.me/BotFather) (команда `/newbot`) |
| `PUBLIC_URL` | публічна HTTPS-адреса, де запущено `server.js` (Telegram Mini App вимагає HTTPS) |
| `ADMIN_IDS` | chat_id адміністраторів через кому (дізнатись — написати `/start` боту [@userinfobot](https://t.me/userinfobot)) |
| `PORT` | порт для express (за замовчуванням 3000) |
| `VERIFY_INIT_DATA` | `true` для продакшна — перевіряє підпис даних від Telegram WebApp |

### Локальний запуск і тест через ngrok

```bash
npm install
ngrok http 3000
# скопіюйте https-адресу з ngrok у PUBLIC_URL у .env
npm start
```

Після цього напишіть боту `/start` — адміністраторам (chat_id яких вказано в
`ADMIN_IDS`) відкриється меню створення заявки, іншим користувачам — реєстрація
як виконавця.

### Продакшн

Для постійної роботи розгорніть на сервері з постійним HTTPS-доменом (наприклад,
через nginx + Let's Encrypt, або на Railway/Render/VPS), встановіть
`VERIFY_INIT_DATA=true` і запускайте процес через pm2 або systemd:

```bash
pm2 start server.js --name tg-service-bot
```

## Дані та постійне сховище (важливо для Railway!)

Всі заявки, виконавці, чати й налаштування зберігаються у файлі `data.json`.
Шлях до нього визначається змінною `DATA_DIR` (за замовчуванням — поруч зі
скриптом). **На Railway (і більшості хмарних платформ) файлова система
контейнера ефемерна: при кожному передеплої чи перезапуску вона скидається,
і `data.json` зникає разом з усіма заявками.**

Щоб цього уникнути, підключіть **Railway Volume**:

1. У сервісі → вкладка **Settings** → **Volumes** → **+ New Volume**
2. Mount path вкажіть, наприклад, `/data`
3. У **Variables** додайте `DATA_DIR=/data`
4. Redeploy

Після цього `data.json` живе на постійному диску, і заявки не зникають ні
при передеплої, ні при перезапуску контейнера.

Для продакшна з великим навантаженням `data.json` можна замінити на
справжню БД (PostgreSQL/MongoDB) — інтерфейс у `db.js` зроблено так, щоб
це було легко зробити, не чіпаючи `server.js` та `bot.js`.


## Статуси заявки

| Статус | Що означає |
|---|---|
| `new` | щойно створена, очікує на виконавця |
| `pending_review` | виконавець підтвердив — очікує перевірки адміном |
| `rescheduled` | виконавець переніс на іншу дату |
| `approved` | адміністратор прийняв виконання |

Якщо адміністратор натискає «Повернути на доопрацювання», статус повертається
у `new`, і виконавець отримує сповіщення.
